# Assumptions and Design Decisions

This document records the business and technical assumptions used by the Transaction Ledger API and dashboard. These assumptions define current behavior; they are not a substitute for additional product or compliance requirements.

## Ledger behavior

1. **Accounts are created by the API.** Account IDs and transaction IDs are UUID strings generated by the backend.
2. **Balances are non-negative.** A debit or transfer is rejected if the source account does not have enough available balance.
3. **Transactions are immutable.** The API supports creating and reading ledger entries, but not updating or deleting them.
4. **A transfer creates two ledger entries.** It creates a debit on the source account and a credit on the destination account, using the same reference ID and description.
5. **Account references are idempotency guards.** A reference ID must be unique within an account. The database constraint is authoritative; a transfer is rejected if the reference already exists on either participating account.
6. **Ledger changes are atomic.** Balance changes and their corresponding transaction records commit or roll back as one database transaction.
7. **Concurrent balance changes are serialized per account.** The backend locks account rows while applying writes. Transfers acquire locks in stable account-ID order.

## Amounts, dates, and ordering

1. **Amounts must be positive decimal values.** The API accepts decimal strings or finite JSON numbers in ordinary decimal notation; signed and exponent notation are rejected.
2. **PostgreSQL `NUMERIC` is authoritative.** The database preserves decimal precision, and API responses serialize amounts as strings to avoid implying JavaScript floating-point precision.
3. **No currency conversion is performed.** Amounts are interpreted in the application's configured display currency; the backend does not attach or validate a currency per account or transaction.
4. **The database generates timestamps.** Clients cannot supply transaction timestamps. Timestamps are returned as ISO 8601 UTC strings.
5. **History is newest-first.** Entries are ordered by `created_at DESC`, with `id DESC` as a deterministic tie-breaker.
6. **Pagination is bounded.** History starts at page 1, defaults to 20 items per page, and allows at most 100 items per page.

## Database and deployment

1. **Supabase provides managed PostgreSQL.** The API connects using the Supabase session pooler URL in the backend's `DATABASE_URL` environment variable.
2. **Schema setup is explicit.** The backend does not run DDL or migrations at startup. `sql/schema.sql` is a bootstrap schema for a new, empty database and should not be treated as a migration for existing tables.
3. **Credentials remain server-side.** The database URL belongs only in the backend environment and must not be exposed through frontend environment variables or source control.
4. **TLS is required.** The current Node `pg` configuration encrypts connections but does not validate the Supabase pooler's certificate chain.
5. **Staff registration is invitation-only.** Admins issue unique one-time keys bound to email addresses; keys are stored as hashes and may be revoked before use.

## Dashboard behavior

1. **The backend does not provide account discovery.** The dashboard keeps a list of accounts that the user created or explicitly linked in browser `localStorage`.
2. **The tracked list is browser-specific.** It is not shared across browsers or devices and is not an authoritative account directory.
3. **Tracking an existing account can use a local display name.** Editing the account name in the dashboard updates the authoritative name through the API.
4. **Untracking does not delete ledger data.** Removing an account from the dashboard only removes the local browser entry; permanent deletion is a separate API operation and is blocked when transactions reference the account.
5. **Displayed balances come from the API.** The frontend does not calculate authoritative balances or invent an aggregate across tracked accounts.
6. **Transaction totals are scoped to the selected account.** The dashboard does not present cross-account reporting as though the API supports it.
7. **Display currency is presentation-only.** Frontend currency formatting does not perform exchange-rate conversion or change stored amounts.

## Out of scope

The current implementation does not define account ownership, audit retention policy, transaction reversal workflows, foreign exchange, fees, scheduled transactions, database migration automation, or production observability. These require explicit product and operational requirements before implementation.
